# forge-codegen — optional, explicit source-materialization tooling

## Verdict

**Reuse as developer tooling, adapt its safety and publication behavior, and exclude it from the default service runtime.** This is a functioning source-materialization engine with a small CLI and library API, not a sketch of a generator. It can support repeatable capability/starter scaffolding while keeping generated Rust visible for review. It does not provide dependency injection, module discovery, service startup, transport adapters, or runtime plugin loading.

## Review scope and evidence

Reviewed the current `main` snapshot on 2026-10-30: complete recursive tree inventory, workspace/package manifests, all five implementation files, source-materialization and built-in-template tests, toolchain/configuration files, and the CI/stack-verification scripts as text. Only `main` was accessible. Exact pins and private source links remain in the private evidence inventory; public references are repository-relative paths and lines.

No generator, build, test, install, CI, or materialization script was executed. The tree has historical checked-in run logs, but those were not treated as proof of the reviewed head. No GitHub Actions workflow appears in the tree; the reviewed commit returned zero GitHub check runs. **Current test success is unverified.** The selected tests are source evidence of intended guarantees, not evidence those guarantees passed here.

## Actual package and API

A one-member workspace contains the `forge-codegen` library and executable. Runtime dependencies include core, command, serde and template capabilities from the framework, plus futures, serialization libraries, SHA-256, Rust syntax parsing, and TOML parsing (`Cargo.toml:1–24`). All four framework dependencies use the same reviewed framework revision. This aligned dependency edge is useful, but the codegen application itself should not become a dependency of applications it generates.

The workspace declares Rust 1.86 and edition 2024, unlike the framework's declared Rust 1.75. No license field or license text was found in this repository's manifest/tree. Clarify license intent and distribution before any public package release; source availability alone is not a reuse grant.

The public API has four operations: `plan`, `materialize`, `check`, and `prune` (`crates/forge-codegen/src/lib.rs:23–41`). A plan lists versioned metadata, workspace root, lock location, and artifacts. Artifacts combine template source, YAML overlay, schema, output-path template, language, and optional list expansion. Templates may be files or named built-ins. Source ownership and SHA-256 input/output digests are written into a deterministic lock model (`model.rs:13–98,216–252`).

## Actual control flow

The CLI parses an operation and plan path, constructs `CodegenApi`, and drives its future with an executor. `CodegenApi` explicitly registers four handlers using the framework's heterogeneous-handler composition API (`command.rs:48–70`). Each handler delegates to a generator operation. This is a particularly useful small example of an application composition root: it wires existing behaviors rather than implementing them itself.

Planning resolves the root, reads and validates inputs, expands repeated artifacts, renders content, validates/normalizes outputs, rejects duplicate output ownership, checks existing files, sorts results, and builds expected lock changes (`engine.rs:43–213`). Materialization prepares writes and stale deletions and applies a staged transaction. Check recomputes the plan and fails when files or lock differ. Prune requires still-declared outputs to be current and validates stale ownership before deletion.

Rust validation invokes `rustfmt` with edition 2024 and then parses the result with `syn`. TOML/JSON/YAML are parsed; shell source is checked with `bash -n`. HTML, CSS, JavaScript, Swift, Markdown and generic text receive normalization rather than language-semantic validation (`engine.rs:606–717`). These are materialized artifacts, not demonstrated working applications. Even valid Rust syntax is not proof that a generated crate type-checks against its dependencies.

## Good boundaries worth retaining

The renderer lives in the framework template capability; this repository owns repository-source installation policy. That differs appropriately from `forge-build`, which produces build-time resources under Cargo's output directory. Codegen provenance is a separate graph from application runtime dependencies: an FSM crate can be generated by this tool while linking only to core.

The engine has useful safeguards: explicit invocation, stable plans, ownership markers, lock checksums, duplicate-output checks, rejection of lexical traversal and outputs resolving outside the workspace through existing symlinks, staged writes, backups, and rollback attempts (`engine.rs:982–1056`; `818–979`). The selected tests exercise visible source generation, drift detection, refusal to overwrite an unrelated manual file, repeated expansion, stale pruning, and path traversal (`tests/source_materialization.rs:54–254`).

These capabilities can generate starter manifests, module roots, adapter skeletons, and contract tests. They do not justify generating all domain behavior. A clear distinction between generator-owned files and handwritten extension files will keep the resulting framework easier to maintain.

## Risks and limits

**Ownership is weaker than edit protection.** Existing and stale files are accepted when either a matching marker is present or the old lock hash matches (`engine.rs:778–815`). Thus a hand-edited generated file retaining its ownership marker may be overwritten or pruned. The drift check detects differences, but materialization/pruning do not guarantee preservation of such edits. Document this policy plainly or tighten it before relying on safe regeneration.

**The multi-file transaction is rollback-capable, not fully atomic or crash-durable.** Files are installed one by one; rollback ignores recovery errors, then transaction cleanup may remove backups (`engine.rs:938–979`). There is no observed interprocess exclusion or durable crash-recovery journal in this implementation. Avoid describing this as a database-grade atomic transaction; add failure injection, recovery and concurrent-run tests before using it on critical generated source.

**Even planning/checking requires local tools.** Rust and shell validation starts external syntax tools. Tool versions matter, and the Rust edition is hard-coded. These commands were intentionally not run during this read-only review. The async command facade also wraps synchronous filesystem/tool execution; it is suitable for this CLI, not evidence of nonblocking high-throughput server behavior.

**The CI wrapper is not read-only verification.** Its exit hook may stage, commit and push generated run logs; CI/fmt paths can also include crate changes, including after a failed run (`scripts/cicd.sh:184–204`). This mixes verification with publication. Before adopting it in a portfolio pipeline, separate check-only commands from explicit release/publish actions and avoid publishing host/user/path metadata captured by logs. No such script was invoked in this review. The stack-verification helper also discards tracked working-tree edits before pulling, applies a source transform, installs a tool and materializes another repository (`scripts/verify-forge-stack.sh:31–44,121–146`). It should not be reused as a harmless verification entry point on an existing worktree.

## Recommended disposition in the new framework

Treat this as an optional development starter: an explicit command helps create a capability package with ports, a bounded handler facade, registration metadata, in-memory tests, and thin transport mappings. Commit readable output and use a non-mutating drift check in CI. Generate the same ordinary Rust registration that could be handwritten; do not make the generator the only way to understand or assemble the application.

Keep transport normalization and destination allowlists in runtime contracts, not templates interpreted at request time. Code generation should help author the route catalog and tests, while the compiled application owns the validated catalog. No dynamic ABI, reflection container, or runtime interpreter is needed.

A useful portfolio demonstration would show a reviewed generation plan, a small visible diff, a clean drift check, and an application that can build and run without the generator installed. That demonstration is proposed. What this review establishes today is the implemented materializer and its explicit dispatch boundary, with the safety caveats above.
