Contracts for opening, retaining, deleting, and expiring saved chats through Forge dispatch.

Dispatch DTOs DAO Sequence diagrams

Dispatch and admission

  1. Browser → Forge web host

    Send application/json to POST /forge/v1/dispatch through the existing access-controlled origin. Forge-Destination identifies the operation. The host checks the configured Host and Origin, the forge_ui session cookie, Forge-CSRF, and Forge-Request-Id. Both Forge-Envelope-Version and Forge-Contract-Version are 1. The typed body must match its destination and request ID.

  2. Forge web host → Forge runner

    After admission, the host sends the validated request to the existing runner’s private POST /v1/dispatch. It uses the same destination, versions and request ID with the runner’s bearer credential. The host keeps browser cookies and CSRF values at the browser boundary. The runner derives the operator from its admitted credential and selects the registered handler.

  3. Forge runner → PostgreSQL

    The runner invokes an operator-scoped DAO operation and returns a bounded, typed result. The browser uses the echoed request_id to match the result to the action that initiated it.

Workspace recovery uses POST /forge/v1/dispatch/workspace, which relays to POST /v1/workspace when durable recovery is enabled. The tab checkpoint stores draft and selection state by chat ID. A linked inference commits the saved transcript in the runner.

Data transfer objects

The examples use sample chat data. Each response event is wrapped in the Forge envelope {"protocol_version": 1, "event": …}.

ChatSummaryDto
chat_id is a stable opaque UUID. title is the display label. updated_at is the UTC time of the most recent committed turn. revision changes with each committed chat mutation, including a retention change. retention is a RetentionPolicyDto.
RetentionPolicyDto
The default is expires, with an inclusive expires_on date 30 days after the first saved turn in UTC. {"kind":"long_term"} is an explicit choice that clears the date. For custom dates, the runner accepts an IANA time_zone and uses UTC when omitted. It returns the derived expires_at UTC instant when the next local calendar day begins.
ChatMessageDto
position, role, and content represent a committed message in transcript order. This tab’s draft is restored separately by stable chat ID.

Delete a saved chat

Forge-Destination: ide.chat.history.delete

DeleteChatRequest

{
  "kind": "chat_history_delete",
  "request_id": "delete-1",
  "chat_id": "4fb285b2-5a53-4caa-90b6-d0aff012c0a4",
  "expected_revision": 8
}

Response event

{
  "kind": "chat_history_deleted",
  "request_id": "delete-1",
  "chat_id": "4fb285b2-5a53-4caa-90b6-d0aff012c0a4",
  "revision": 9
}

The interface confirms deletion before sending. On success, it removes the chat and the draft keyed to that chat.

409 means the expected revision is stale. Refresh the saved version before attempting another change. 404 covers missing, expired, deleted, and out-of-scope chat IDs. An admitted operation’s error result echoes request_id with a typed code such as {"kind":"chat_history_failed","request_id":"delete-1","code":"revision_conflict"}. A failed open preserves the active transcript and draft.

PostgreSQL data access

ChatHistoryDao belongs to the Forge runner. Every operation takes the operator scope established at admission. Stable chat IDs connect committed messages, retention, and authorized run links. Tab selections and drafts refer to those IDs.

commit_transcript(owner, chat_id, messages)
Save the transcript with the default expiration on its first committed turn. Subsequent turns retain the existing policy.
list(owner, limit, cursor)
Read available summaries in descending last-committed-turn time, with the stable ID as the cursor tie-breaker. Omit transcripts, drafts, tombstones, and already-due chats.
get(owner, chat_id)
Read the summary and ordered committed messages from a consistent snapshot. Apply the same ownership and expiry predicates as the list.
set_retention(owner, chat_id, expected_revision, policy)
Lock the chat row, verify its revision and availability, and persist the resolved policy with the next revision in one transaction.
delete(owner, chat_id, expected_revision)
Lock the chat row, compare the revision, and commit the tombstone and content removal together. Preserve the ID, revision, and removal reason so stale writers cannot recreate it.
expire_due(now, batch_limit)
Run bounded batches in the existing runner scheduler. Recheck the policy, due instant, and candidate revision under the row lock, then use the same removal transaction as manual deletion. A policy change committed before that check takes effect.

The removal transaction covers the committed transcript, chat-owned linked run content, and recoverable checkpoint copies. Use explicit chat ownership links to determine which records belong to the chat. Check the tombstone at checkpoint save, restore, and late run completion so an open tab or a finishing request cannot revive the chat.

The runner imports shared workspace transcripts as saved chats. Separate copies in older tabs, unlinked runner snapshots, and existing backups follow their existing retention scope.
